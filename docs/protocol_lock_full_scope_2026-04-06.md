## 2. Locked Protocol — Baseline 2 (Token/QR Provisioning)

### 2.1 Design rationale

B2 models OOB-assisted provisioning: a provisioning token is generated by the
operator/server before the session and shared out-of-band to the device (simulating
what a QR scan or printed label would accomplish in a real deployment). The device
presents the token to claim a provisioning slot.

This is:
- Clearly distinct from B1 (no auth, no identity)
- Clearly distinct from B3 (no asymmetric crypto, no certificate)
- Fast to implement (single HTTP POST, no mbedTLS on ESP32)
- Measurable with the same T_start/T_end pattern already established

### 2.2 Trust model

- **Shared secret token**: a hex string generated by the server before each run.
- **Out-of-band delivery**: simulated by printing the token to the host console and
  manually setting `TOKEN_VALUE` in the ESP32 firmware define before building.
  This represents the operator scanning a QR code or reading a device label.
- **No asymmetric crypto** on the ESP32 side — the token is the only credential.
- **Single-use**: the server marks a token as consumed after first valid use. A
  second attempt with the same token must return 401.
- **Session binding**: each run uses a fresh token; tokens are indexed by `run_id`.

### 2.3 Message flow

```
[ESP32]                              [Cloud Emulator / Pi relay]

1. T_start = esp_timer_get_time()
2. DNS lookup -> resolve server IP
3. TCP connect to WEB_SERVER:WEB_PORT
4. HTTP POST /provision
   Body: {
     "run_id":   "<run_id>",
     "device_id": "esp32_01",
     "token":    "<TOKEN_VALUE>"
   }
                                     5. Validate: token present in store for
                                        this device_id and not already used
                                     6a. If valid:
                                         mark token used
                                         HTTP 200 {"run_id":...,
                                                   "device_id":...,
                                                   "provisioning_status":"ok"}
                                     6b. If invalid/used:
                                         HTTP 401 {"error":"invalid or expired token"}
7. Parse HTTP status code
8. T_end = esp_timer_get_time()
9. MEASURE log
10. close socket
```

### 2.4 Token format and QR payload concept

Token: 32 hex characters (128 bits of entropy), e.g. `a3f9c2e1...`

QR payload concept (for report narrative): the token string is what a QR code
would encode. In the testbed, the QR is simulated by the operator printing the token
from the server console and manually configuring the firmware define. The report
documents this as "OOB token delivery — simulated QR scan".

In firmware: `#define PROVISION_TOKEN "a3f9c2e1b8d4f7a2c0e5d9b3f1e8a6c4"`

A different token is used for each experimental run. For reproducibility, the tokens
for a given session are generated once, logged in the host terminal, and stored in
`data/raw/b2_token_session_<date>.txt` (tokens only, no secrets that unlock real
systems).

### 2.5 Required endpoints

**New endpoint in `cloud_emulator/api/app.py`:**

```
POST /provision
Request body: {run_id, device_id, token}
Success: 200 {"run_id":..., "device_id":..., "provisioning_status":"ok"}
Invalid token: 401 {"error":"invalid or expired token"}
Missing fields: 400 {"error":"..."}
```

Token store: a Python dict in memory, pre-loaded at startup from a session config.
For the test session: `TOKEN_STORE = {"esp32_01": ["token_run1", "token_run2", ...]}`.
After each success: move consumed token to a `used_tokens` set.

Log: append to `cloud_emulator/api/logs/provision_log.jsonl` (separate from
`enroll_log.jsonl` to keep logs per-method).

**Via Pi:** The existing Pi relay at `gateway/pi/iot_gateway_relay.py` needs to
add `/provision` to its `ROUTES` dict. One line change; no other Pi-side logic
needed (server-side validation stays in cloud emulator).

### 2.6 ESP32-side steps

1. Configure token: set `#define PROVISION_TOKEN "..."` before build.
2. Connect to Wi-Fi (via `example_connect()`).
3. For each run: DNS lookup, TCP connect, POST /provision body, parse status, log MEASURE.
4. No mbedTLS needed. No CSR. No cert storage.
5. Firmware structure: clone `baseline1_http`, change GET to POST with body.

### 2.7 Pass/fail criteria

- **PASS**: HTTP 200 received, `provisioning_status == "ok"` in body.
- **FAIL**: HTTP 401 (wrong/expired token), HTTP 4xx/5xx, or `http_status == -1`
  (socket timeout or network error).

MEASURE line target: `http_status=200` for all 5 runs (first run of each uses a
fresh token per run_id).

### 2.8 MITM scenarios for B2

| Scenario | Attack | Expected outcome | Testbed method |
|----------|--------|-----------------|----------------|
| A (passive sniff) | Capture traffic, inspect token in plaintext | Token visible in plaintext HTTP → attacker can reuse it | tcpdump/Wireshark on hotspot |
| C (replay) | Replay captured POST /provision with same token | Token already marked used → server returns 401 | Replay captured bytes manually |
| D (rogue server) | Point ESP32 at attacker IP, collect token | ESP32 sends token to attacker who can forward to real server | Change WEB_SERVER to attacker IP |
| B (modification) | Modify token in transit | Server validation fails → 401 | arpspoof + modify bytes |

Expected result summary: B2 is **vulnerable to passive sniffing** (token in
plaintext). This is expected and is the point of the comparison.

### 2.9 Expected evidence artifacts

- `capture/b2_token_serial_<date>.txt` — UART log
- `capture/pcaps/b2_normal_run_<date>.pcap` — normal run traffic
- `capture/pcaps/b2_mitm_<date>.pcap` — MITM scenario capture
- `cloud_emulator/api/logs/provision_log.jsonl` — server-side per-request log
- `data/raw/b2_live_rerun_<date>_evidence.md` — evidence note

## 3. Locked Protocol — Proposed Method: Gateway-Brokered Two-Phase Enrollment

### 3.1 Design rationale

The Proposed Method makes the Pi an **active security participant** rather than a
transparent relay. It adds:
1. **Local device authentication** at the gateway (Pi validates a per-device token
   before any cloud interaction happens).
2. **Short-lived session gating** (Pi issues a session token that the device must
   present for CSR enrollment — ties phases together and limits replay window).
3. **Full certificate issuance** via the existing cloud CA (Pi never holds CA key).

Compared to existing methods:

| Property | B1 | B2 | B3 | Proposed |
|----------|----|----|----|----|
| Device auth | None | Token (OOB) | None (trust on first use) | Token (OOB) + session gating |
| Credential output | None | ACK only | X.509 cert | X.509 cert |
| Crypto on ESP32 | None | None | ECDSA key gen + CSR | ECDSA key gen + CSR |
| Pi role | Dumb relay | Dumb relay | Dumb relay | Active gatekeeper |
| Replay resistance | None | Single-use token | None | Short-lived session token (30s) |
| MITM resistance | Low | Low (plaintext) | Medium (cert binds identity) | High (dual-layer) |

### 3.2 Trust assumptions

- ESP32 has a **per-device pre-shared auth token** (different from B2 token — this
  is a long-term device identity secret, not a single-use provisioning token).
- Pi maintains a **device registry**: a dict `{device_id: expected_token}`.
  This registry is a local config file on the Pi (not committed — analogous to
  Wi-Fi credentials).
- Cloud emulator is the CA. Pi has network access to the cloud emulator.
- Session tokens issued by Pi are short-lived (30 seconds) and single-use.
- No TLS in this testbed version (same hardware constraint as all other methods).
  The MITM section documents what TLS would add.

### 3.3 Exact onboarding phases

```
PHASE 1 — Local Gateway Authentication
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[ESP32]                                [Pi Auth Service :8090]

T_start = esp_timer_get_time()
DNS + TCP connect to Pi:8090
POST /gateway/auth
  {device_id: "esp32_01",
   token:     "<DEVICE_TOKEN>"}
                                       Lookup device_id in registry
                                       Validate token matches expected
                                       Generate session_token = hex(urandom(16))
                                       Store {session_token: (device_id, expires_at)}
                                         expires_at = now + 30s
                                       Return 200 {session_token: "...",
                                                   expires_in: 30}
Parse response, extract session_token
close Phase 1 socket
T_phase1_end = esp_timer_get_time()

PHASE 2 — Gateway-Brokered Certificate Enrollment
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[ESP32]         [Pi Auth Service :8090]     [Cloud Emulator :5000]

Generate EC keypair + CSR (mbedTLS, same as B3)
TCP connect to Pi:8090
POST /gateway/enroll
  {device_id:     "esp32_01",
   session_token: "<session_token>",
   run_id:        "<run_id>",
   csr_pem:       "-----BEGIN CERTIFICATE REQUEST-----\n..."}
                Validate session_token:
                  - exists in store?
                  - not expired?
                  - device_id matches?
                Mark session_token used (prevent replay)
                Forward POST /enroll to cloud emulator
                  {run_id, device_id, csr_pem}
                                        Sign CSR with CA
                                        Return {device_cert_pem, ca_cert_pem}
                Return 200 to ESP32
                  {run_id, device_id,
                   device_cert_pem, ca_cert_pem}
Parse HTTP status, receive cert
T_end = esp_timer_get_time()
MEASURE log
close socket
```

### 3.4 What the Pi does

- Runs `gateway/pi/iot_gateway_proposed.py` (new service, port 8090).
- Holds the device registry in memory (loaded from a local config at startup).
- Phase 1: validates device auth token, issues 30-second session token.
- Phase 2: validates session token (not expired, not reused, device_id matches),
  forwards CSR to cloud emulator, returns result.
- Logs each phase event to `gateway/logs/proposed_service_<date>.log`.
- Does NOT hold the CA private key.

### 3.5 What the cloud emulator does

- No changes to `cloud_emulator/api/app.py`.
- `POST /enroll` is reused exactly as-is (same request/response schema as B3).
- Pi calls the emulator on behalf of the ESP32 — the ESP32 never connects directly
  to the emulator in the Proposed Method.

### 3.6 What the ESP32 does

- Phase 1: one HTTP POST to Pi:8090/gateway/auth (small JSON body, no crypto).
- Phase 2: generate EC keypair + CSR (mbedTLS, same as B3), then one HTTP POST
  to Pi:8090/gateway/enroll (medium JSON body, ~1.8 KB for CSR PEM).
- Receives and verifies HTTP 200, extracts cert from response.
- No TLS on ESP32 side (same constraint as all other methods).

### 3.7 Crypto operations at the device

- Phase 1: none (token is a plain string match).
- Phase 2: mbedTLS `mbedtls_ecp_gen_key` (SECP256R1) + `mbedtls_x509write_csr_pem`
  (SHA256) — identical to B3. This is the dominant crypto cost.
- Net result: same key gen / CSR cost as B3, plus Phase 1 round-trip overhead.

### 3.8 Replay protection

- Phase 1 token: device's long-term auth token. If captured, an attacker could
  impersonate the device to get a session token — but only before Phase 2 is
  completed (the session token is single-use with a 30s window). This is a known
  limitation without TLS. Documented in MITM section.
- Phase 2 session token: single-use, 30s TTL. Replay of a captured session token
  fails after expiry or after first use.

### 3.9 Pass/fail criteria

- **PASS (single run)**: both Phase 1 and Phase 2 return HTTP 200; `device_cert_pem`
  received and non-empty in Phase 2 response.
- **FAIL**: any of: Phase 1 returns 401/403/5xx; Phase 2 returns 401/403/5xx;
  `http_status == -1` (socket/network error); session token expired between phases.

### 3.10 MITM scenarios for Proposed Method

| Scenario | Attack | Expected outcome |
|----------|--------|-----------------|
| A (passive sniff) | Capture Phase 1 + Phase 2 traffic | Auth token and session token visible in plaintext; but 30s window limits usability |
| C (replay Phase 2) | Replay captured POST /gateway/enroll with valid session token | Fails: session token already consumed (single-use) |
| C (replay Phase 1) | Replay captured POST /gateway/auth | May succeed within 30s if attacker is fast; fails after window |
| D (rogue gateway) | Point ESP32 at attacker Pi:8090 | Attacker receives auth token; can relay to real gateway within 30s |
| B (token modification) | Modify token in transit | Phase 1 validation fails → 401/403 |

Expected result: **significantly stronger replay resistance than B1/B2**; still
vulnerable to passive sniffing (no TLS). This positions the Proposed Method as
the strongest of the four evaluated, consistent with report intent.

### 3.11 Expected evidence artifacts

- `capture/proposed_serial_<date>.txt` — UART log (Phase 1 + Phase 2 timings)
- `capture/pcaps/proposed_normal_<date>.pcap` — normal run traffic
- `capture/pcaps/proposed_mitm_<date>.pcap` — MITM scenario
- `gateway/logs/proposed_service_<date>.log` — Pi-side event log
- `cloud_emulator/api/logs/enroll_log.jsonl` — cloud-side signing log (reused)
- `data/raw/proposed_live_rerun_<date>_evidence.md` — evidence note

## 4. Measurement Definitions

### Common to all methods

```
T_start    = esp_timer_get_time()  just before first DNS lookup
T_end      = esp_timer_get_time()  just after last read() returns 0 on final socket
latency_ms = (T_end - T_start) / 1000

heap_before = heap_caps_get_free_size(MALLOC_CAP_8BIT)  at T_start
heap_after  = heap_caps_get_free_size(MALLOC_CAP_8BIT)  just before close()
heap_delta  = heap_after - heap_before

MEASURE printf format (same as B1/B3):
  MEASURE run_id=%d heap_before=%lu heap_after=%lu heap_delta=%ld
          start_ms=%u end_ms=%u latency_ms=%u http_status=%d
```

### B2 — additional measurements

- No crypto timing (no mbedTLS calls). Body size is small (~80 bytes). Fast expected.
- `http_status`: 200 = provisioning accepted, 401 = token rejected, -1 = network fail.

### Proposed — additional measurements

Two separate timing spans to log per run:

```
Phase 1 timing:
  T_p1_start = just before Phase 1 DNS lookup
  T_p1_end   = after Phase 1 last read()
  latency_p1_ms

Phase 2 timing:
  T_p2_start = just before mbedTLS key gen (includes crypto cost)
  T_p2_end   = after Phase 2 last read()
  latency_p2_ms

Total:
  latency_total_ms = T_p2_end - T_p1_start

MEASURE line (Proposed):
  MEASURE run_id=%d ... latency_p1_ms=%u latency_p2_ms=%u latency_total_ms=%u
          http_status_p1=%d http_status_p2=%d
```

Heap measurement: one `heap_before` at T_p1_start, one `heap_after` at Phase 2 close.

### Minimum runs per method

Per report commitment (N >= 10):
- **B2**: 10 runs, one fresh token per run. All runs must show `http_status=200`.
- **Proposed**: 10 runs, fresh `device_token` per session (device registry entry
  stays the same; session tokens are per-run). All runs must show both statuses 200.

For dataset integration: rows go into `data/processed/results.csv` with
`baseline` column = `B2` or `Proposed`.

## 6. Recommended Implementation Order

### Phase A — B2 (2–3 sessions)
1. Add `POST /provision` to `cloud_emulator/api/app.py` with in-memory token store
   and `provision_log.jsonl` logging.
2. Add `/provision` to Pi relay ROUTES (1 line).
3. Create `esp32_firmware/baseline2_token/` — clone B1 structure, change to
   POST /provision with `PROVISION_TOKEN` define and JSON body.
4. Configure sdkconfig, set token, do one dry-run (5 runs, direct to laptop).
5. Capture serial log to `capture/b2_token_serial_<date>.txt`.
6. Verify `provision_log.jsonl` has 5 correct entries.
7. Run MITM Scenario A (passive sniff) and Scenario C (replay).
8. Do 10-run final session, capture evidence, write evidence note.
9. Append B2 rows to `data/processed/results.csv`.

1. Create `gateway/pi/iot_gateway_proposed.py` — Phase 1 auth endpoint +
   Phase 2 enroll endpoint, device registry, session token store, logging.
2. Deploy to Pi, test with `curl` from laptop.
3. Create `esp32_firmware/proposed_gateway/` — two-phase firmware.
4. Configure sdkconfig, set device token, do one dry-run (5 runs via Pi).
5. Capture serial log with Phase 1 + Phase 2 timings.
6. Verify Pi service log and emulator log.
7. Run MITM scenarios (A, C, D).
8. Do 10-run final session, capture evidence, write evidence note.
9. Append Proposed rows to `data/processed/results.csv`.

### Phase C — MITM completion and report integration
1. Ensure all four methods have MITM scenario A (passive sniff) captured.
2. Run replay and rogue-server scenarios on B2 and Proposed.
3. Update `data/processed/final_results.csv` with all 40+ rows.
4. Regenerate analysis figures (Figures 7.5/7.6 + new figures for B2/Proposed).

## 7. Open Questions

**Q1: Token distribution for B2 fresh-token-per-run.**
Simplest implementation: pre-generate 10 tokens at session start, set them as an
array in the ESP32 firmware (`const char *TOKENS[] = {...}`), and index by run number.
The same array is configured in the server's TOKEN_STORE. This avoids per-run
manual intervention. The array is logged once before the session starts.

**Q2: Proposed firmware — heap stack size.**
The Proposed firmware makes two sequential HTTP calls and one mbedTLS key gen.
Use the same 8192-byte task stack as B3. If Phase 1 and Phase 2 overlap in heap
usage, increase to 10240. Verify empirically on first dry-run.

**Q3: Pi service for Proposed — port conflict with relay.**
The new service runs on port **8090** (relay stays on 8080). Both can run
simultaneously without conflict. The ESP32 firmware for Proposed points at port
8090; B1/B3 via Pi continue to use port 8080.
